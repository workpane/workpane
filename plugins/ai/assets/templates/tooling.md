# Command line tools and automation engineering

## Recognize the project

- Find the language and entry point: `pyproject.toml` with `[project.scripts]`, `go.mod` with a `cmd/` folder, `Cargo.toml` with `[[bin]]` or `src/main.rs`, `package.json` with a `bin` field, or executable shell scripts with a shebang.
- Find the argument parser the project uses (`argparse`, Click or Typer in Python, `flag` or Cobra in Go, `clap` in Rust, `node:util` `parseArgs`, Commander or yargs in Node) and follow it. Never introduce a second parser.
- Read the existing commands end to end: how they print, how they report errors, which exit codes they return, where they read configuration and how they are tested.
- Find the build, test, lint and release commands in `Makefile`, `justfile`, `noxfile.py`, `package.json` scripts and the CI workflows.
- Treat the documented interface (commands, flags, output format, exit codes, environment variables) as a public API that scripts depend on. Changing it is a breaking change.

## Architecture

- Separate the command layer from the logic: the command parses arguments, builds a typed options value, calls a function that does the work, and renders the result. The logic never reads `argv`, the environment or global state directly.
- Inject the outside world: standard streams, environment lookup, the clock, the working directory and the file system root are parameters of the core function, so tests run it in process.
- Return results and errors from the core, and decide exit codes and output format in one place at the top.
- For tools with subcommands, give each subcommand its own module with the same shape. Shared flags such as `--verbose`, `--quiet`, `--config` and `--output` are defined once.

## Project structure

```
mytool/
├── pyproject.toml           # Metadata, entry point, dependencies, tool configuration
├── src/mytool/
│   ├── __main__.py          # Enables "python -m mytool"
│   ├── cli.py               # Parser, subcommands, exit codes, output rendering
│   ├── config.py            # Configuration loading and precedence
│   ├── commands/            # One module per subcommand, logic only
│   └── paths.py             # Platform directories for config, data, cache and state
├── tests/
│   ├── test_cli.py          # Subprocess and in-process command tests
│   └── golden/              # Expected outputs for golden tests
└── scripts/                 # Repository automation, not shipped
```

- Adapt the tree to the language: `cmd/mytool/main.go` with `internal/` in Go, `src/main.rs` with `src/cli.rs` and `src/commands/` in Rust, `bin/mytool.js` with `src/` in Node.
- Repository automation scripts live in `scripts/` or the task runner and are written in the language the project already uses for them.
- Use the documentation comment convention of the language (docstrings, `///`, JSDoc) for public functions only where the project writes them, and keep comments rare. The help text is the user documentation and comes from the parser.

## Command-line interface

- Provide `--help` and `-h` on the tool and every subcommand, generated by the parser, with a one-line summary, usage, every flag with its default, and an example for non-obvious commands. Provide `--version`.
- Follow the conventions of the platform: long flags with two hyphens, short flags for frequent options, `--` to end options, `-` for standard input or output where a file is expected.
- Write data to standard output and everything else (progress, warnings, errors, prompts) to standard error, so `tool | other` and `tool > file` stay clean.
- Offer a machine-readable format (`--json` or `--output json`) for any output a script may parse, keep it stable, and never mix human text into it. Human output may change, machine output is a contract.
- Return meaningful exit codes: `0` on success, `1` for a general failure, `2` for wrong usage, other documented codes for distinct failures, and `130` after an interrupt. Never exit `0` after a failure.
- Write errors as one clear sentence that says what failed and what to do, with the offending path or value quoted. Show stack traces only with `--verbose` or a debug variable.
- Detect a terminal with `isatty` on the stream you write to. Show colors, spinners and progress bars only on a terminal, honor `NO_COLOR` and the project's `--color` flag, and keep logs line-based when output is redirected.
- Prompt only when standard input is a terminal, and provide a flag (`--yes`, `--force`, or a value flag) for every prompt so the tool works in scripts and CI.
- Ask for confirmation before destructive operations and offer `--dry-run` that prints exactly what would change without changing it.

## Patterns and practices

- Make operations idempotent: running a command twice leaves the same state, and a create of something that exists either succeeds unchanged or fails clearly as documented.
- Resolve configuration with a fixed precedence: flags over environment variables over the project config file over the user config file over defaults. Document each variable and file, and show the effective value in verbose or a `config` subcommand.
- Store user files in the platform directories: on Linux follow XDG (`$XDG_CONFIG_HOME` defaulting to `~/.config`, `$XDG_DATA_HOME` to `~/.local/share`, `$XDG_STATE_HOME` to `~/.local/state`, `$XDG_CACHE_HOME` to `~/.cache`), on macOS `~/Library/Application Support` and `~/Library/Caches`, on Windows `%APPDATA%` and `%LOCALAPPDATA%`. Use `platformdirs` in Python, `os.UserConfigDir` and `os.UserCacheDir` in Go, `directories` in Rust, or `env-paths` in Node rather than hand-built paths.
- Build paths with the path library (`pathlib`, `filepath.Join`, `std::path::Path`, `node:path`), never by joining strings with `/`. Accept both separators on Windows and handle spaces and non-ASCII names.
- Read and write text with an explicit encoding (UTF-8) and preserve the line endings of files you edit. Keep `.gitattributes` rules for scripts that must stay LF.
- Write files atomically: write to a temporary file in the same directory, flush, then rename over the target, so an interrupted run never leaves half a file.
- Handle signals: on `SIGINT` and `SIGTERM` stop work, clean up temporary files and child processes, and exit with `130` or `143`. A second interrupt exits at once.
- Handle a closed pipe quietly: `tool | head` must not print a traceback or panic. In Python catch `BrokenPipeError` at the top, and in Rust handle write errors instead of `println!` in data paths.
- Bound work from outside: timeouts on network calls, limits on file sizes read into memory, and streaming for large inputs.
- Log with levels controlled by `-v`, `-q` or an environment variable, to standard error.

## Data, networking and persistence

- Parse structured input with real parsers (JSON, TOML, YAML in safe mode, CSV with the standard module) and validate it into typed values before acting.
- Never parse the human output of other programs when they offer a machine format (`--json`, `--porcelain`, `-print0`). Set `LC_ALL=C` when parsing output that a locale could change.
- Call external programs with an argument vector (`subprocess.run([...], check=True)`, `exec.CommandContext`, `std::process::Command`, `execFile`), check their exit status and capture standard error for the message.
- Cache with a key that includes every input that changes the result, in the cache directory, and make the cache safe to delete.

## Security

- Never accept secrets as command-line arguments, because they appear in `ps`, shell history and CI logs. Read them from an environment variable, a file with restrictive permissions, the system keychain, or standard input (`--password-stdin`).
- Create files that hold secrets with mode `0600` and directories with `0700` on POSIX.
- Never build shell strings from input. In shell scripts quote every expansion (`"$var"`, `"$@"`), use arrays for argument lists, and pass `--` before user-supplied names.
- Create temporary files with `mktemp` or the language's secure temporary file API, never a predictable name in `/tmp`.
- Verify downloads by checksum or signature before running or extracting them, and extract archives with path checks that refuse entries escaping the destination.

## Shell scripts

- Start with `#!/usr/bin/env bash` and `set -euo pipefail` when the script needs Bash, or `#!/bin/sh` with POSIX syntax only when it must run anywhere. Do not use Bash features under `sh`.
- Quote every variable, use `[[ ]]` in Bash, `$(...)` instead of backticks, and `local` variables in functions.
- Clean up with `trap 'rm -rf "$tmp"' EXIT` right after creating temporary state.
- Check for required commands with `command -v` and fail with a clear message.
- Keep scripts short. When a script grows logic, data structures or error handling beyond a page, write it in the project's main language.
- Lint with `shellcheck` and format with `shfmt -d` (or `-w`) using the project's indentation flags.

## Performance

- Start fast: defer imports of heavy modules and avoid network calls at startup. Measure startup with `hyperfine` when it matters.
- Stream input and output line by line or in chunks instead of reading everything into memory.
- Parallelize independent work with a bounded pool and keep output ordered when users expect order.

## Tests

- Test the core logic in process with injected streams, environment and file system roots, using `t.TempDir()`, `tmp_path`, `tempfile` or the equivalent of the language.
- Test the command layer end to end with subprocess tests that run the built tool and assert on exit code, standard output and standard error separately. Use `CliRunner` for Click, `testscript` for Go, `assert_cmd` or `trycmd` for Rust, `bats-core` for shell, and `execa` or `child_process` in Node.
- Use golden files for help text and output formats, compared exactly and refreshed only through an explicit update flag or environment variable, then reviewed in the diff.
- Cover usage errors, missing files, permission errors, a closed pipe, an interrupt, non-terminal output, `--json` output and `--dry-run`.
- Run the tests on every operating system the tool supports, since paths, line endings and signals differ.
- Measure coverage with the language's tool (`pytest --cov=mytool --cov-branch --cov-report=term-missing`, `go test -coverprofile`, `cargo llvm-cov`, `vitest --coverage` or `c8`), and for subprocess tests enable subprocess coverage the tool supports, such as `go build -cover` with `GOCOVERDIR`.

## Tooling and quality gates

- Run the formatter, linter and type checker of the language with the project's configuration: `ruff format`, `ruff check` and `mypy` or `pyright` for Python, `gofmt` and `golangci-lint` for Go, `cargo fmt` and `cargo clippy -- -D warnings` for Rust, the project's ESLint and TypeScript `tsc --noEmit` for Node.
- Run `shellcheck` on every shell script and `shfmt -d` for formatting.
- Keep the help output and the documentation in sync, and generate manual pages or shell completions from the parser when the project ships them.

## Build, configuration and release

- Version with SemVer and print it from `--version`, taken from the package metadata or build flags, never typed twice.
- Distribute the way the project does: `pipx install` or `uv tool install` for Python packages with `[project.scripts]`, `go install module/cmd/mytool@version`, `cargo install --locked`, the `bin` field of `package.json` with a `#!/usr/bin/env node` shebang, a Homebrew formula or tap, and release binaries for every supported platform and architecture.
- Publish release binaries with a `SHA256SUMS` file and, where the project does, signatures or provenance attestations. Build them in CI from a tag, never on a laptop.
- Keep dependencies locked (`uv.lock`, `go.sum`, `Cargo.lock`, `package-lock.json`) and the runtime dependency set small.

## Pitfalls

- Printing progress or warnings to standard output and corrupting piped data.
- Exiting `0` after an error, or crashing with a traceback on a usage error.
- Prompting in CI and hanging forever because standard input is not a terminal.
- Passing tokens as flags, or printing them in verbose output.
- Hard-coded `/` separators, `~` paths or `/tmp` that break on Windows.
- Unquoted shell variables that split on spaces or expand globs.
- Partial writes left behind by an interrupt.
- Changing flag names or JSON fields without a deprecation path, breaking scripts that depend on them.

## Definition of done

- Every command and flag has accurate `--help` text, and `--version` prints the released version.
- Data goes to standard output, diagnostics to standard error, and machine output is available and stable where scripts consume it.
- Exit codes are correct for success, failure, usage errors and interrupts.
- Configuration follows the documented precedence, and user files live in the platform directories.
- Destructive operations confirm or require a flag, and `--dry-run` exists where changes are made.
- Writes are atomic, interrupts clean up, and a closed pipe exits quietly.
- No secret is read from or printed into arguments or logs.
- Paths and line endings work on every supported operating system.
- Shell scripts pass `shellcheck` and `shfmt`.
- Unit and subprocess tests pass on every supported system, golden files are reviewed, and coverage was read from the coverage tool.
- The documented installation method installs the tool and the installed command runs.
