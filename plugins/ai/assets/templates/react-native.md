# React Native engineering

## Recognize the project

- Read `package.json` first: the versions of `react-native`, `react` and `expo`, the scripts, and the package manager given by the lock file (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` or `bun.lock`). Use that package manager only.
- An `app.json`, `app.config.ts` or `app.config.js` with an `expo` key and the `expo` package means an Expo project. Without `android` and `ios` folders in the repository it uses Continuous Native Generation, so native folders are generated by `npx expo prebuild` and never edited by hand. With committed native folders and no Expo, it is a bare React Native project.
- An `app` folder with `_layout.tsx` files means Expo Router. A `NavigationContainer` means React Navigation configured by hand.
- Read `tsconfig.json`, `babel.config.js`, `metro.config.js`, `eas.json`, the ESLint configuration (`eslint.config.js` or `.eslintrc*`), `jest.config.js` or the `jest` key, and the `ios/Podfile` and `android/app/build.gradle` of a bare project.
- Check `newArchEnabled` and the React Native version. The new architecture (Fabric, TurboModules, bridgeless mode) is the default in recent versions and the only one in the newest, so every native library you add must support it.
- In Expo projects, install native packages with `npx expo install <package>` so the version matches the SDK the project pins, and check the project with `npx expo-doctor`.
- Find the commands in the scripts: `npx expo start`, `npx expo run:ios`, `npx expo run:android`, `npx react-native run-ios`, `npm test`, `npx tsc --noEmit`, `npm run lint`, and the EAS profiles in `eas.json`.

## Architecture

- Keep the same layers a good web React app has: screens compose feature components, components render props, hooks hold view logic, and a data layer of API clients and query hooks talks to the server. Business rules live in plain TypeScript modules with no React or native imports.
- Separate server state from client state. Server state (fetched, cached, refetched) belongs to TanStack Query or RTK Query. Client state that many screens share belongs to Zustand or Redux Toolkit, whichever the project uses. Local state stays in `useState` or `useReducer`.
- Organize by feature. A feature exposes its screens, hooks and types through a small public surface and never reaches into the internals of another feature.
- Write native code only when no maintained library or Expo module provides the capability. Prefer the Expo Modules API (Swift and Kotlin) in Expo projects, and a TurboModule or Fabric component with a typed Codegen spec in bare projects.

## Project structure

```
app/                          # Expo Router routes, _layout.tsx files and screens as thin route files
src/
  features/
    orders/
      components/             # Components of the feature
      hooks/                  # Query and view hooks such as useOrders
      api.ts                  # Requests and response schemas of the feature
      types.ts
  components/                 # Shared design system components
  theme/                      # Tokens: colors, spacing, typography, light and dark
  lib/                        # API client, storage wrappers, i18n setup, logger
  stores/                     # Zustand stores or Redux slices for shared client state
  i18n/                       # Translation resources per locale
assets/                       # Images and fonts
modules/                      # Local Expo modules or TurboModules with their native code
e2e/ or .maestro/             # Detox tests or Maestro flows
app.config.ts                 # Expo configuration and config plugins
eas.json                      # Build, submit and update profiles
```

- Route files in `app` stay thin and render a screen from its feature. In React Navigation projects, screens live in their feature and navigators in `src/navigation`.
- One component per file named in PascalCase, hooks named `useSomething`, and colocated tests named `*.test.tsx` or under `__tests__` as the project does.

## Patterns and practices

### TypeScript and components

- Keep `strict` on and use no `any`, no non-null assertions on values that can be missing, and no `@ts-ignore`. Validate external data with the schema library the project uses, such as Zod, and derive types from schemas.
- Write function components with typed props. Keep them small and pure, and lift logic into hooks.
- Follow the rules of hooks and of `useEffect`: effects synchronize with outside systems, never derive state that can be computed during render, and clean up subscriptions, timers and listeners.
- Use `useMemo` and `useCallback` where profiling or the identity of a dependency demands them, or rely on the React Compiler when the project enables it.

### Navigation

- With Expo Router, type routes with its typed routes support, read parameters with `useLocalSearchParams` and validate them, group routes with `(group)` folders and protect routes in layouts with redirects or `Stack.Protected` as the project does.
- With React Navigation, declare param lists per navigator, type `useNavigation` and `useRoute` with them, and use static configuration where the project adopted it.
- Pass identifiers in routes, never whole objects, and load data in the destination through the query cache.
- Treat every deep link and universal link as untrusted input.

### Server and client state

- Use TanStack Query with query keys built from a factory per feature, `staleTime` set deliberately, `useMutation` with invalidation or optimistic updates that roll back on error, and `focusManager` and `onlineManager` wired to `AppState` and network status as the docs describe for React Native.
- Keep Zustand stores small with selectors (`useStore(s => s.value)`) to avoid rerenders, or Redux Toolkit slices with `createSlice` and typed hooks. Never copy server data into a client store.
- Persist client state only through a storage adapter, such as MMKV, and only what must survive a restart.

### Errors, logging and configuration

- Wrap the app and risky subtrees in error boundaries with a recovery screen, and report errors to the crash service the project uses.
- Remove `console.log` from committed code and use the logger in `lib`, without personal data or tokens.
- Read configuration from `app.config.ts` `extra` or `EXPO_PUBLIC_` variables in Expo, or `react-native-config` in bare projects. These values are inlined into the bundle and are public.
- Localize with the library the project uses, such as `i18next` with `react-i18next` or `expo-localization` with a catalog, and format with `Intl`, which Hermes supports.

### Documentation comments

- TypeScript uses TSDoc or JSDoc (`/** ... */`) only on exported APIs where the project already writes it. Comments stay rare.

## Data, networking and persistence

- Use one API client (`fetch` wrapper, `ky` or `axios`) in `lib` with a base URL, timeouts through `AbortController`, authentication headers and a single-flight token refresh. Cancel requests with the signal TanStack Query passes to query functions.
- Parse every response with a schema before it reaches components.
- Store small key-value data with `react-native-mmkv` (fast, synchronous, not a secret store unless its encryption key itself lives in secure storage) or AsyncStorage when the project has it. Store relational data with `expo-sqlite`, op-sqlite or WatermelonDB as the project does, with migrations.
- Store tokens, refresh tokens and credentials only in `expo-secure-store` or `react-native-keychain`, which use the Keychain and the Android Keystore. Never in MMKV without encryption, AsyncStorage, Redux persist or files.

## Interface

- Use the design system components and tokens of `theme`, with light and dark schemes read from `useColorScheme`. No literal colors or sizes in components.
- Respect safe areas with `react-native-safe-area-context` (`SafeAreaView` or `useSafeAreaInsets`), handle the keyboard with `KeyboardAvoidingView` or the keyboard library the project uses, and test on small phones and tablets.
- Follow platform conventions: native stack navigation, platform back behavior on Android, haptics where the platform uses them, and `Platform.select` only for real differences.
- Accessibility: set `accessibilityRole`, `accessibilityLabel`, `accessibilityHint` and `accessibilityState` on custom touchables, group related content with `accessible`, hide decorative views with `importantForAccessibility="no-hide-descendants"` and `accessibilityElementsHidden`, keep targets at least 44 points (`hitSlop` helps), and let text scale with `allowFontScaling` and `maxFontSizeMultiplier` only where a layout truly cannot grow.
- Use `Pressable` instead of the older touchables, and `expo-image` or the image library the project uses for caching.

## Security

- Never ship secrets in JavaScript. The bundle, `EXPO_PUBLIC_` values and `extra` are readable by anyone who downloads the app. Call a backend that holds the secret.
- Keep tokens in secure storage as above, require biometrics for sensitive actions with `expo-local-authentication` or `react-native-keychain` access control, and clear secure storage on logout.
- Keep App Transport Security and the Android cleartext defaults. Expo config plugins and `app.config.ts` must not add `NSAllowsArbitraryLoads` or `usesCleartextTraffic` for production.
- Validate deep link parameters and never navigate to or perform an action from them without checks.
- Over-the-air updates through EAS Update or another service ship code to devices: use code signing for updates where the project configures it, update only JavaScript and assets compatible with the runtime version, and never ship a native change as an update.
- WebView (`react-native-webview`): restrict `originWhitelist`, handle `onShouldStartLoadWithRequest`, never inject secrets into pages and validate every message from `onMessage`.
- Review native permissions in config plugins and manifests, with usage descriptions for iOS and only the Android permissions the feature uses.

## Performance

- Keep Hermes enabled. Profile with React DevTools, the Hermes profiler and the native profilers in a release build, never in development mode.
- Render long lists with FlashList (or `FlatList` when the project uses it) with stable `keyExtractor`, memoized item components and no inline heavy work in `renderItem`. Follow the props of the FlashList version the project pins.
- Run animations on the UI thread with Reanimated shared values, `useAnimatedStyle` and worklets, and gestures with `react-native-gesture-handler`. Do not animate with `setState`.
- Avoid rerendering whole screens: select narrow store slices, split contexts, and keep frequently changing values out of context.
- Load images at their displayed size, and defer work after interactions and the first frame.
- Watch bundle size and startup: remove unused dependencies and avoid large polyfills.

## Tests

- Unit and component tests use Jest with the preset the project uses (`jest-expo` or `react-native`) and React Native Testing Library: `render`, `screen.getByRole`, `getByLabelText` and `getByText`, `userEvent` or `fireEvent`, and `findBy` queries for async results. Query by role and label the way users perceive the screen, and by `testID` only as a last resort.
- Wrap components in the providers the app uses (query client with retries off, theme, navigation and i18n) through a shared `renderWithProviders` helper.
- Mock native modules with the mocks their libraries publish, and mock the network at the client boundary or with MSW where the project uses it. Never mock the component under test.
- Test hooks with `renderHook`, stores directly, and schemas and pure modules with plain unit tests.
- End-to-end tests use Detox (`detox build` and `detox test` with the configuration in `.detoxrc.js`) or Maestro (`maestro test .maestro/`) as the project does, against a release-like build, covering the critical flows.
- Run coverage with `npx jest --coverage` or the test script with `--coverage`, read `coverage/lcov-report/index.html` or the text summary, and respect `coverageThreshold` in the Jest configuration.

## Tooling and quality gates

- Type check with `npx tsc --noEmit` and keep it at zero errors.
- Lint with ESLint using the configuration of the project, such as `eslint-config-expo` or `@react-native/eslint-config`, with the hooks rules on, and run `npx eslint . --max-warnings=0` when the project treats warnings as errors.
- Format with Prettier (`npx prettier --check .`) as configured.
- In Expo projects run `npx expo-doctor` after dependency changes, and use `npx expo install --check` to align versions with the SDK.
- In bare projects run `pod install` in `ios` after native dependency changes and commit `Podfile.lock`.

## Build, configuration and release

- Use EAS Build profiles in `eas.json` (development, preview, production) with environment variables set per profile through EAS environment variables or secrets, never committed. Build with `eas build --profile production --platform all` and submit with `eas submit`.
- Bump `version` in the app configuration for user-visible releases and let EAS manage build numbers with `autoIncrement` when the project uses remote versioning. In bare projects, set `versionCode` and `CFBundleVersion` the way the project does.
- Set `runtimeVersion` with a policy so over-the-air updates reach only compatible binaries.
- Modify native projects in CNG projects through config plugins, so `npx expo prebuild --clean` reproduces them. Write a config plugin instead of patching generated folders.
- In bare projects, sign iOS with fastlane or Xcode settings and Android with an upload key from CI secrets, and build release variants with `./gradlew bundleRelease` and `xcodebuild archive`.
- Upgrade React Native with the Upgrade Helper or the Expo SDK upgrade guide one version at a time, and check every native dependency for support of the new architecture.

## Pitfalls

- Editing the generated `ios` or `android` folders of a CNG project, which the next prebuild discards.
- Installing a native package with a version that does not match the Expo SDK, or one that does not support the new architecture.
- Expecting a native change to arrive through an over-the-air update.
- Putting secrets in `EXPO_PUBLIC_` variables, `app.json` or the bundle.
- Storing tokens in AsyncStorage or unencrypted MMKV.
- Copying query results into Redux or Zustand, which makes two sources of truth.
- Inline anonymous components and objects in list items, which break memoization and recycling.
- Measuring performance in development mode with the debugger attached.
- Assuming web APIs exist. React Native has no DOM, and polyfills must be explicit.
- Testing only on one platform when the change touches layout, keyboard, permissions or navigation.

## Definition of done

- The command `npx tsc --noEmit`, ESLint and Prettier pass with zero errors and no new warnings.
- The command `npx expo-doctor` passes in Expo projects and native dependencies match the SDK the project pins.
- The change runs on both iOS and Android, on a small phone and a large screen, in light and dark mode.
- Server state lives in the query layer, shared client state in the store of the project, and nothing is duplicated.
- Text is localized, colors and spacing come from the theme, and controls have roles, labels and adequate targets.
- Tokens are in secure storage and no secret is in the bundle or configuration.
- Lists use FlashList or `FlatList` correctly, and animations run on the UI thread.
- Native changes are expressed as config plugins in CNG projects, and `Podfile.lock` and lock files are committed.
- Jest and React Native Testing Library tests cover the behavior, end-to-end flows pass where the project has them, and the coverage report was read.
- The production build profile succeeds for each affected platform.
