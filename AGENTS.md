# Workpane Engineering Standard

This file is the authoritative engineering standard for Workpane. It records the product architecture, the ownership of every part, the implementation rules and the completion gates. A newer explicit product requirement takes precedence when it intentionally replaces a rule here, and this file is updated in the same change.

## Product

- Workpane is a native desktop workspace for developers that brings terminals, a code editor, a browser, local servers and AI agents into one window.
- The C++ half is the host and the Lua half holds every feature, each one a plugin the reader turns on and off or writes.
- The product supports macOS from 13.3, Linux and Windows on x86_64 and arm64. CMake selects the minimum macOS deployment target before its project command, preserves a supported target supplied by a parent and refuses an older one. The bundle declares the selected target as its minimum.
- The implementation uses C++20, CMake from 3.29 and Ninja through the task runner in `make.py`.
- The product version and the build number are separate declarations, and the application information, settings and macOS bundle carry both, with the build number used for the bundle version.
- Native automated tests use GoogleTest with CTest discovery, build task tests use the standard Python unittest library through CTest and every test runs in a process of its own.
- Warnings are errors for every first-party target, with the full GCC and Clang warning set including conversions and shadowing.

## Repository organization

- The folder `src/app` holds the application, which owns the window and the frame loop, the product, which owns everything else and runs without a window in the suites, the command line, the core preferences and the build information.
- The folder `src/ui` holds the fonts, the icons, the painter, the textures and the widgets, with the theme in `ui/theme`, the components, nodes and surfaces in `ui/model`, the shell with its mode bar, dialogs, notifications and settings view in `ui/shell`, Markdown in `ui/markdown` and one folder per family of components under `ui/components`.
- The folder `src/scripting` holds the Lua runtime, the bridge and one host per area of the SDK, `src/persistence` holds SQLite, the preference documents, the plugin tables and the transfer of the configuration, and `src/platform` holds what each system does its own way.
- The folders `src/audio`, `src/execution`, `src/files`, `src/http`, `src/json`, `src/localization`, `src/logging`, `src/process`, `src/text` and `src/time` each hold the area they are named for, and `src/Result.h` and `src/Error.h` declare the result and the structured error every layer answers.
- The folder `lua/workpane` holds the SDK, `plugins` holds the bundled plugins in one folder per identifier, and `assets/fonts` holds the bundled faces.
- The folder `cmake` holds the pinned dependencies, their patches in `cmake/patches`, the sources of each platform, the staging of resources, packaging, warnings, sanitizers and coverage, and `extras` holds the images and the files of each platform package. The folder `examples` holds independently configurable source consumers.
- The folder `tests` holds one folder per suite and the shared harnesses and fakes in `tests/support`, `docs` holds the references, `make.py` runs every task and `.github/workflows` holds the Build and Release workflows.

## Reusable foundation

- The target `Workpane::Core` is the static C++ source library containing the native application and product, all visual components and hosts and the Varn runtime dependencies. It propagates C++20 and its complete target graph to source consumers.
- The option `WORKPANE_BUILD_APPLICATION` enables the reference Workpane executable, bundled features and product packaging only for the top-level build by default. Subdirectory consumers default to the library, and the application suites follow the application option and require it.
- The functions `workpane_add_application` and `workpane_install_application` in `cmake/WorkpaneApplication.cmake` are the public source integration. Each application declares its own identity, receives its own generated entry point, resources and install component and includes only explicitly supplied plugin folders. An application with no plugin folders starts the core shell and settings with every component available.
- The type `ApplicationIdentity` carries the product name, version, build, organization, identifier and directory names, is checked before storage opens and crosses to Lua through application information. Native credentials use the application and plugin identifiers together, and the default data directory of a derived product uses its stable identifier. The reference desktop product explicitly retains its data directory.
- The Lua fields `workpane.app.version` and `workpane.app.buildNumber` belong to the application, while `workpane.app.engineVersion` and `workpane.app.engineBuildNumber` describe the Workpane base. The current SDK declares the application identity and process completion contracts together.
- Resource staging belongs to each application target, tracks additions and removals and copies only the SDK, fonts, selected plugin roots and optional logo. Duplicate supplied plugin identifiers are refused during configuration. The parent project owns its package and release metadata.
- Application target names remain unique when case is ignored, because their native bundles and resource directories must remain distinct on every supported filesystem. The runtime's position independent compilation is scoped to its dependencies and preserves the parent project's compilation requirement.
- The library hosting suites link the core directly without the desktop application's Windows process manifest, so native Unicode paths, image and font loading, filesystem errors and HTTP resolution are checked independently of the process code page. The linked TLS release is checked against the source release the dependency graph configured.
- The guide `docs/foundation.md` documents source consumption, CMake arguments, runtime identity, storage isolation, layouts, installation and C++ hosting. The complete parent project in `examples/plugin-app` builds a custom plugin application and a plugin-free application against the same core.

## Dependencies

- Every dependency is fetched by CMake from a pinned archive with its SHA-256, none is taken from the system except the platform libraries, and every patch is a CMake script in `cmake/patches`.
- The runtime searches its pinned archive headers through explicit ordinary include paths before compiler environment paths, so an installed archive library never supplies its headers. The build suite resolves an object's compilation database output from its declared compilation directory, resolves Ninja dependencies from the build directory and checks the actual runtime object's recorded dependencies against both pinned archive headers. Clang's nullability extension is accepted only for the third party runtime, while first party warnings remain unchanged.
- The OpenSSL source release and its recipe target version are pinned together, and its recipe records the source identity before deciding whether to reuse its build directory. A changed source replaces the generated configuration and compiled libraries before any consumer links them.
- The product fixes the minimum CMake policy version of its pinned dependencies on every configure, overriding the cache of a build folder so Debug and Release never select different policy floors.
- Varn fetches CPM and every library it builds from archives pinned by their digests, so the archive digest and its declared patches pin every source the runtime builds, and the audits refuse any declaration or download of the product without its digest.
- A patched archive is extracted again whenever one of its patches changes, and the cache of every workflow is keyed on the patches, so a patch always meets the pristine sources it was written for.
- The runtime's OpenSSL recipe is patched through its own digest-keyed archive to select the native ARM64 Visual C++ build environment on Windows ARM64, rather than invoking the environment script without an architecture.
- Dear ImGui draws the interface through GLFW and the OpenGL core profile, and FreeType rasterizes its text, reading the pictures of color emoji with the libpng and the zlib the runtime builds and serves to every library of the build.
- FreeType explicitly enables its PNG and zlib decoders, including when a build directory already holds cached disable options, and the suite rasterizes the package manager symbols through the actual system fallback faces.
- MD4C reads CommonMark and GitHub Markdown extensions from a pinned archive, while the product owns layout, selection, links, tables and code highlighting, and raw HTML remains literal text.
- Dear ImGui is patched to size a color emoji face that holds only fixed strikes by its em, scaling its glyphs from the smallest strike reaching it, and to give a character Unicode declares default ignorable no room and no glyph when no face holds it.
- Varn runs the Lua half, embedded as a shared library through its C interface, with its static dependencies built as position independent code.
- The embedded Lua auxiliary source-file loader opens native wide filenames on Windows while retaining Lua's own BOM, shebang, text and error handling. Filesystem strings crossing the C interface remain UTF-8, including a direct host whose executable declares no process code page.
- Varn exposes an owned HTTP exchange with the response promise and an idempotent cancellation handle, which interrupts its existing transport when cancelled or collected, and the buffered and streaming entry points share their respective request implementations.
- Varn bounds an archive listing by its entry count before allocating any rows, accepts a smaller bound from its caller and refuses entries without readable size metadata, so a package is inspected before it is extracted.
- The web view is webview on macOS and Linux, patched to keep the data of its pages under the data directory, and WebView2 through the headers and the static loader of its SDK on Windows.
- The code editor is ImGuiColorTextEdit at a pinned commit, patched to center its rows, leave finding to the find bar of the product, keep the numbers of its markers and squiggles after a deletion, draw the guide of a block only beside the lines indented past it, move to the ends of a line with Command and the arrows on macOS, read only the lines its document still holds after the text shrinks and bound a pointer outside the window before it becomes a position.
- The terminal is libvterm, patched to keep faint text and OSC 8 hyperlinks and to give every character the width the shell behind it gives it, and GLFW is patched to let the product take part in the input methods of macOS and X11.
- The native dialogs are portable-file-dialogs, patched to start their helper programs through `posix_spawn` with the signals of a shell and no descriptor of the product, the sounds play through miniaudio, the icons are the Lucide font and the only persistence engine is SQLite.

## Architecture

- The C++ half owns the window, the frame loop, the components, the database, localization and every platform service, and knows no feature.
- The Lua half owns every feature, and the core application settings are the only Lua the product carries outside a plugin.
- The two halves meet only through host functions and events carrying JSON, and no pointer or implementation type crosses between them.
- The application owns what exists because there is a window, and the product owns everything else, so the suite composes exactly what ships.
- The frame loop draws only when something changed and otherwise waits without a deadline for an event or a wake, Lua wakes it when work reaches it from another thread and otherwise lets it sleep until its next timer, so no coroutine keeps it ticking, only input, a host call that can change the screen, a picture or a font that arrived and a component asking for a frame count as a change, so work that only logs, stores or reads never draws, every change is followed by the settling frames ImGui needs to lay out new content, including a tooltip or a menu that just appeared, and frames keep coming while input waits in the queue of ImGui, which spreads input that arrives at once over several frames.
- Each turn of the loop gives Lua a bounded time, in which the runtime repeats its passes while they make progress, so a chain of promises settles in one turn and no plugin holds a frame past that bound.
- A minimized window draws nothing, so every canvas and animation pauses until it is restored, while Lua, the main thread queue and the updates of components keep running.
- The frame loop reads visibility again after native events and service callbacks run, and the frame scheduler owns the hidden to visible transition, drawing and settling a restored idle window without waiting for another input event.
- The window remembers only the place it has on screen, written once it settles and on close, so a window closed while minimized opens again where the reader last saw it.
- The interface thread draws, runs Lua and owns every component, never waits for storage, a process, a worker or the network, and work done elsewhere comes back through the main thread queue.
- An SSH control wait propagates a failed readiness or cancellation signal instead of retrying an already settled failure, and every fixture retains the resolver of a signal it intends to keep pending.
- The process host bounds both the bytes and the fragments waiting for the interface, merges adjacent fragments of the same stream, pauses its serving threads while either bound is full and wakes them after delivery, and closes that mailbox before stopping processes so shutdown releases every producer still waiting.
- A program that carries a binary protocol selects `binaryOutput`, so its exact output bytes cross the JSON bridge in Base64 and reach its ordered SDK handler as binary strings. Text streams use incremental UTF-8 decoding, and both modes retain the same ownership, exit ordering and mailbox backpressure.
- A plugin ends an owned pipe program's input explicitly through `workpane.process.endInput`, which refuses further writes immediately and lets its native writer deliver all accepted bytes before closing the pipe. Output and actual exit continue independently, and a pseudo-terminal refuses pipe EOF.
- A program selecting `pullOutput` keeps its exact bytes behind native byte and fragment bounds until its single accepted reader asks for them. Its reader waits for actual output or exit, partial reads retain their storage credit until the chunk is released and the exit follows the final byte. Plugin withdrawal releases the reader and drains discarded output before joining serving threads.
- Stopping a pull program discards unread output so its blocked producer can finish without another read, retains an accepted reader until the native exit and delivers that actual completion to its reader and exit handler. Terminal cleanup starts immediately on stop and its wake mutex is never held while reading, writing, resizing or closing the native terminal.
- Native macOS SSH session cleanup uses its system automation runtime to query actual session identities and signal only matching processes from a bounded PID listing, retains the session leader during termination and kills it last, so descendants in separate terminal process groups remain owned. Its source code runs through SSH without installing an executable.
- An SSH command's native completion travels through its private ownership channel independently of its standard streams, so binary diagnostics and terminal rendering never carry status markers. The ownership dispatcher correlates command replies, delivers admitted completion once and ignores a late completion for a retired monotonic identity without reopening it.
- Owned POSIX terminal shutdown sends native hangup before bounded forced cleanup, so an interactive shell can commit its private history through its normal shutdown. Pipe programs retain termination signaling, every producer records its kind before its session becomes visible and session leaders remain owned until the final kill.
- POSIX SSH producers preserve the account's original creation mask for the program they launch, while their own ownership files and staging remain private. Their supervisor ignores a broken output pipe so its lease observer still cleans resources after transport loss.
- Windows SSH programs enter a reserved native job before launching a target suspended in its own child job. The target joins that job before it resumes, its descendants end before final stream draining and its actual native completion is published through account-owned state. Pipe input passes through the same owned buffered stream as source loading and reaches synchronous target pipes, while terminal targets inherit the native console directly.
- An editor save invalidates its metadata stamp after committing its exact bytes instead of attaching a later metadata observation to those bytes. Its next poll verifies content even outside the recent-change window, preserves later unsaved text and reports an external edit that crossed save completion.
- A save accepted while its workspace is available returns its actual committed revision even when that workspace disconnects before the reply, while new work remains refused and edits made during the save stay unsaved. Terminal history and startup files live in private directories owned by the same native supervisor, and ordinary staging creation failures return structured filesystem errors without ending a healthy connection.
- A POSIX pipe producer duplicates its original input before asynchronous launch and closes that duplicate in the target, so the shell's background-input rules preserve every accepted byte and ordinary EOF without leaking another descriptor.
- Remote document replacement verifies its exact revision and content again before publication, preserves existing permissions and publishes a new file exclusively. Windows replacement captures the complete destination DACL and its protection state and reapplies them through a metadata-only handle that remains attached to the published bytes, so inherited access entries survive replacement and a concurrent pathname change cannot redirect permission updates. Staging belongs to the connection supervisor and its accepted transfer handles close before staging removal.
- Native Linux file moves use the current GNU coreutils operation that refuses copying between filesystems, while macOS uses its native exclusive rename API, so moving an entry never becomes an implicit copy or replaces an entry created by another writer.
- The SFTP transport invokes OpenSSH's standard subsystem through the binary process bridge, negotiates its declared protocol, parses bounded fragmented packets and matches each reply to one accepted request. It refuses unknown identities, duplicate or mismatched replies, excessive metadata and data beyond the requested read. A deadline or an abandoned accepted request closes the channel and settles every waiter, and server diagnostics never enter its structured failures.
- The library `WorkpaneSystem` owns the file replacement, path, JSON, text, process and pseudo-terminal services shared by the desktop application and its local terminal session executable, so every source is compiled once.
- An SSH workspace capability reserves a bounded scope for one caller and one connection instance before accepting native program group creation, keeps admission until accepted preparation, provider-owned requests and cleanup settle, refuses another caller and any supplied process group and closes the whole connection if consumer cleanup fails.
- A consumer group is reserved synchronously before its queued open, receives a monotonic connection-owned identity and retains admission through cleanup. Opening never creates a missing reservation, so removing a completed group cannot revive a late request or impose a lifetime limit on workspace reuse. A group stops every producer before joining any program, and another group cannot touch its processes.
- Remote SSH connects through the installed OpenSSH client, uses its SFTP subsystem for file transport and runs the bundled POSIX shell or Windows PowerShell sources through the remote operating system. The connection operates offline with its installed system tools, SSH configuration and credentials.
- The SSH request dispatcher validates and copies each bounded declaration before admission, keeps ordinary requests in a bounded queue and reserves independent capacity for lease renewal, cancellation and live stream readers. SFTP validates packet identities, lengths, attributes, statuses and binary data before delivery and never exposes a raw peer diagnostic.
- A Windows SFTP document payload has owner-only permissions before publication, because a private parent directory alone does not prevent native traversal privileges from reaching a known child path. Publication applies the destination inheritance or preserves its existing access list.
- A remote document save checks its content revision, stages its complete bytes beside the destination in a private folder, preserves an existing file's permissions and checks its previous content again before replacement, while publishing a new file never replaces a destination another writer created, and every staged folder is removed when the operation ends.
- A private staging folder is created with its restricted access from the start, mode 0700 on POSIX and a protected Windows access list granting full access only to its explicitly declared account owner, so no complete temporary file ever waits for its access to be narrowed.
- Every database statement runs on the database thread, and every image is decoded on the worker pool.
- Remote document revisions hash the exact received binary bytes through `workpane.files.hash`, whose host validates its owner and encoded byte bound before the worker decodes, validates the canonical transport and computes SHA-256, so no complete remote document is hashed on the interface thread.
- A plugin creates private filesystem staging through the worker host, using mode 0700 on POSIX and a protected account owner access list on Windows, which refuses an existing path or a missing parent, and the plugin waits for its accepted writes before removing their folder.
- File digests run on the worker pool through a bounded streaming SHA-256 reader, and shutdown cancels the reader between chunks.
- The picture decoder reads PNG, JPEG and the first frame of GIF, and a decoded picture keeps its pixels only until the renderer created its texture, so every picture costs its texture alone, a picture declaring more pixels on a side than the renderer accepts, with a smaller bound for a data address such as the icon of a page, is refused from its header before it is decoded, and a picture no drawn frame asked for over a bounded number of frames is released and decoded again when it shows.
- The current process completion contract carries the exit code and a failure boolean, which includes every nonzero exit and native failure without claiming to distinguish a shell exit from a signal. Workspace transport failures carry a separate structured problem, explicit cancellation returns its cancellation status and a producer ending without completion fails within its bounded metadata wait. The SDK level changes with this contract and the profile snapshot.
- A host function answers `{ ok, value }` or `{ ok, error }` with a structured error of `code`, `message` and `detail`, and a function that waits answers through a request number and the reply event.
- A value Lua sends to the host nests within a bounded depth, since the runtime reads back fewer levels than it writes, and a reply or an event the runtime could not read is a structured error instead of a nil.
- The startup opens the product, attaches the window and starts Lua in that order, and a failure in any step is shown in a native alert in the language the reader chose once the product read it, and in the language of the system before.
- The Lua bootstrap receives the resource directory as application information and loads SDK modules directly from that directory, so a valid installation path never becomes Lua source or a search path expression. A missing or invalid SDK module fails startup instead of selecting a module outside the shipped SDK.
- The window system is ended whenever it started, even when its window could not open, and every wake a platform service or the runtime holds is cleared before the product stops.
- A display without the OpenGL core profile the renderer needs refuses the window with `window_opengl_unavailable`, and any other refusal answers `window_create_failed`, each carrying the reason the window system gave.
- A second instance on the same data directory is refused before the database is opened, and the database closes before the data directory is released.
- A walk and a search bound every inspected entry, including empty folders, preserve readable siblings when an inner folder is inaccessible and carry incomplete inspection through their shared visitor, and a walk, a search or a listing of folders leaves out an entry it cannot read and says it is incomplete when a bound or a quit stopped it, and quitting stops each one still running between entries instead of waiting for the whole folder. A listing bounds inspected entries, reports unreadable metadata as incomplete and stays complete when its exact bound reaches the end.
- Every file host operation validates an absolute UTF-8 path without NUL before constructing a native path, so the operating system never reads or replaces the truncated prefix of a malformed name.
- The HTTP host validates the document root's UTF-8 and refuses NUL before constructing a native path, and the native server refuses NUL in either its bind address or its absolute root before lookup or binding, so no malformed endpoint can serve a truncated folder name. Request paths are percent-decoded and checked as UTF-8 without NUL before native path construction, with malformed text refused as a bad request.

## Lua SDK and plugins

- The SDK in `lua/workpane` is the only code that reaches the host table, which it removes from the global environment as it loads.
- Every call of the API of a plugin carries the identity of that plugin, so no plugin can speak for another one, and the host refuses a plugin its registry does not hold.
- Every plugin declares the level of the SDK it is written for, and the manager refuses by name a plugin declaring any other level, so a change of the API that would break a plugin raises the level in the same change and no plugin breaks in silence.
- The API grows by adding functions, fields and events, and a change to what an existing function takes or answers, or to the payload of an event or a capability, raises the level of the SDK.
- The identifier of a plugin is checked before its code runs and the core identifier is refused, and a plugin publishes, subscribes, provides, requests, reads the log and starts tasks only between its registration and its withdrawal.
- The bridge closes before the hosts are released, so a call that arrives later, such as one from a finalizer, answers a structured error.
- Private file staging reserves its native ownership before accepting directory creation, starts every operation through its bounded scope, retains accepted file waiters through plugin withdrawal, refuses a scope closing itself from its own operation and removes only a directory it created, and the file host outlives the Lua runtime so accepted runtime filesystem work finishes before final staging cleanup.
- A plugin is a folder named after its identifier holding `plugin.lua` and `translations.lua`, with other files loaded through `include` and images and data kept in `assets`.
- Every plugin follows one layout: `plugin.lua` only declares the plugin and wires its start, stop and capabilities, `view.lua` builds its destination view, parts of the view layer live under `views`, `settings.lua` builds its settings sections, `preferences.lua` keeps the values they edit, `store.lua` owns its tables and every other module is named for what it is.
- Plugins are discovered in the bundled folder and then in the plugin folders the reader adds in the core settings, which take effect after a restart, and a plugin whose identifier a folder before it already answered is refused.
- A plugin environment receives its own copies of the standard library tables, of every module it requires and of the lists of `workpane.app`, the string metatable answers its name, the metatables of the SDK are locked and a plugin reads only the metatables it set itself, so no plugin can change a function or read a value another plugin uses.
- The SDK refuses a mistaken call with a structured error, never with an assertion.
- A plugin reaches only the standard Lua functions, a restricted `os`, the allowed Varn modules and its own API, and never another plugin.
- A plugin keeps an explicitly requested password through `workpane.credentials`, whose host validates its owner and bounded key and value, runs native credential operations on a worker and stores them in the account Keychain on macOS, Credential Manager on Windows and the desktop Secret Service on Linux. Secrets never enter preference documents, configuration export, public snapshots or diagnostics, and an unavailable credential service answers a structured failure without stopping the plugin. An SSH profile records only its choice to save a password, and a profile without that choice never depends on native credential storage for authentication, editing or removal.
- A plugin asks for OpenSSH credentials through `workpane.process.askpass`, whose loopback listener checks its private token in constant time, bounds prompts and replies, runs its prompt handler in a protected task and closes before its owner is withdrawn, while `WorkpaneAskpass` gives an accepted answer only to the process that asked and prints no diagnostic or secret on failure.
- Plugins are ordered by their dependencies, started in that order and stopped in reverse order, and a plugin with a missing, refused or cyclic dependency is refused by name.
- The SDK marks global product shutdown before the first plugin stops and exposes it through `workpane.app.isClosing`, so a consumer keeps an interrupted run recoverable instead of recording service withdrawal during shutdown as a task failure. New task and schedule admission stops at that same boundary.
- When the product closes each stop runs for its share of a bounded time, so one stop that never ends holds the others only for that share, and the plugins reading the log stop after every other plugin, once what the other stops wrote reached them.
- A plugin that fails to register or start is withdrawn completely, with its destinations, bands, settings, subscriptions, watchers, preference documents, servers, programs, sounds, dialogs and surfaces, while its catalog stays so the Plugins section still names it.
- The plugin manager in `lua/workpane/plugins.lua` keeps every discovered plugin with its state of discovered, waiting, starting, running, stopping, disabled, unavailable or refused, writes every change of state to the log under the category `plugins` with the state it left, the state it entered and the reason, and is the only code that starts and stops plugins.
- A view, a band or a settings section the shell asks of a plugin while it starts is held and built once its start finishes, so a preloaded view comes back whole when its plugin is turned off and on, and the Plugins section shows the passing states while they last.
- Every switch of the Plugins section follows what the reader chose and waits while any change of the plugins runs, a plugin turned off stays off even when its code cannot be read, and closing the product waits for the change in progress before the plugins stop.
- The catalog of every discovered plugin is installed at discovery, and a plugin may declare a `descriptionKey` that the Plugins section shows under its title, which every bundled plugin declares.
- The reader turns any discovered plugin on and off while the product runs: turning one off stops its running dependents first, runs each stop for a bounded time and withdraws each one, turning one on reads its folder again and starts it and every plugin that waited for it, and one change of the plugins runs at a time.
- Windows SFTP transfer paths use forward slashes and a leading slash before a drive letter, so POSIX and Windows clients both keep them absolute. UNC transfer roots retain their leading double slash.
- Remote SSH authentication owns a bounded set of credential channels for its exact connection, serializes interactive prompts without blocking the interface and reuses a password or key passphrase only for the first matching prompt of another channel. A repeated prompt invalidates that cached answer, channel cancellation releases queued prompts without allowing them to overtake an active dialog and connection closure clears every secret before joining its listeners.
- Remote executable discovery runs as a bounded request on the established native ownership channel and follows the account search path before explicitly supplied directories, so discovering editor tooling does not consume a program reservation or launch another SSH connection. Windows batch programs use the system command interpreter with expansion-sensitive arguments refused before admission.
- A command transport that actually ended waits only for the bounded delivery of its owned completion record, then releases its reservation and reports a structured failure if that record never arrives. A live silent command keeps its output reader pending until data, completion or owned cancellation, and never times out for being idle.
- POSIX SSH scope creation resolves its newly owned temporary folder to a physical path before announcing it, so private program and terminal resources follow the same canonical boundary as the workspace. Accepted filesystem requests retain their provider completion independently of the caller's deadline, and a closing workspace keeps its admission until those requests finish while rejecting queued work that has not started.
- Direct SSH account discovery reads the operating system account record and canonicalizes its home before exposing read-only account resources. Repository discovery inspects ancestors for a file or directory named `.git` without requiring Git, and each inspection remains confined to its declared home or repository root.
- Remote SSH profiles retain explicit account names without configuration variable expansion, pass them through the native SSH account argument and preserve configured host aliases and raw IPv6 addresses for both command and subsystem channels.
- An enabled plugin whose persisted table structure is newer than or differs from its current declaration, or whose start explicitly refuses invalid persisted rows, is withdrawn, backed up as a complete database snapshot under its private `plugin-data-recovery` folder and reset before one fresh start. Only the core may request recovery, the database thread owns the complete backup and atomic erasure, and backup or erasure failure preserves the old data and refuses the plugin with its reason. A disabled plugin stays untouched, unrelated plugin data stays in place and arbitrary start failures are never a reason to erase data.
- The position the reader gave the switch of each plugin is kept in the `pluginSwitches` core preference, a plugin declaring `offByDefault`, as the components gallery, Flappy Bird and Task Hero do, stays off until the reader turns it on, a plugin whose dependency does not run waits instead of starting, and the data of a plugin that does not run, installed or not, can be erased after a destructive confirmation. After a successful erase, an enabled discovered plugin is read and started again with its running dependencies, while a disabled or removed plugin stays stopped. A cancelled or failed erase preserves its data and does not start it. Incompatible stored schemas are explained in the Plugins section even when Logs cannot start.
- A plugin keeps its values through `workpane.preferences.define` with typed rules of `boolean`, `integer`, `number`, `string`, `list`, `record`, `map` and `any` that nest, validate a whole value with the path of its first problem and read a stored value they refuse as its default with one warning.
- A preference store answers get, values, set, update, reset, watch and control, applies a change in memory at once, writes the whole document with a revision and puts the committed document back when the latest write fails, exactly as the host does.
- A settings section edits a preference through the control its store builds, bound to the key both ways, instead of a hand written listener, and a plugin may keep several named documents.
- A plugin can watch copied directory snapshots at each state change through the SDK, whose protected handlers belong to the subscriber and are removed on withdrawal, so a provider releases consumer resources when that consumer is withdrawn, while its stopping hook retains access for graceful shutdown.
- A plugin follows the capabilities it uses with `workpane.capabilities.watch` and the language and theme of the reader with `workpane.app.watch`, instead of reading them once.
- A plugin contributes bands across the top or the bottom of the window, each built as a surface `band:<plugin>:<item>` once the workspace is ready, with a height of zero or within the bounds the shell declares, which its plugin changes with `workpane.shell.resizeBand`.
- Focus mode of the Terminal zooms the focused terminal, so zooming one focuses it and another terminal taking the focus ends the zoom, and the Terminal announces a change of its workspace only when the snapshot it offers changed.
- The Web Server serves local document roots.
- The Web Server keeps a bounded list of the newest requests of each running server, newest first, renders them once for every batch that arrives in one turn of the loop, and treats a link to a terminal that closed as no link.
- The Web Server inspects a requested folder through SDK metadata and canonicalizes its original path without trimming filename characters, so a trailing backslash remains part of a POSIX folder name and a failed inspection opens no configuration form.
- A plugin plays WAV, FLAC and MP3 files of its assets through `workpane.audio`, the audio thread opens the device and every file, a sound that cannot be heard ends at once with its reason in the log and never fails the call, and the sounds of a plugin stop with it.
- The Flappy Bird plugin is a game in a destination and the Task Hero plugin an adventure that runs by itself in a band at the bottom, and each keeps its rules in a module without drawing that the suite drives tick by tick.

## Persistence

- One SQLite database in the data directory holds the preference documents, the schema version of every plugin and every plugin table.
- A preference document belongs to one owner, the core, a plugin or a named document of a plugin written `plugin:name`, is read whole at startup and written whole on the database thread, a failed write puts the committed document back, and a stored document that is not an object is left out with a warning instead of stopping the start.
- The core reads its language, theme and plugin folders through `CorePreferences` by the rules the core settings of Lua declare, and a value it refuses reads as its default.
- A plugin table is named with the plugin identifier and two underscores as its prefix, an identifier never holds two hyphens in a row so no prefix starts another one, and an authorizer installed for every statement of a plugin enforces it.
- The authorizer lets a plugin change its schema only in its migrations, creating, altering and dropping tables, indexes, views and triggers under its exact lowercase prefix, a trigger only on a table of its own and a foreign key only to a table of its own, lets SQLite reach its own schema tables only while it changes the schema of an owned object, refuses pragmas, attachments, transaction commands and table renames, and interrupts a plugin statement and a migration that pass their bounded times and any plugin statement still running as the database closes.
- A plugin transaction rolls back only while it is still open, so a failure SQLite already rolled back reaches the caller as itself, and a binding or a stored real that is not a finite number is refused both ways.
- Plugin migrations are lists of statements a plugin declares in its definition, which the manager applies before every start once, atomically and in order, a stored version newer than the list is refused, and the stored tables, indexes, views and triggers of a plugin are compared both ways at every start with the ones its migrations create in memory, so a stored object its migrations do not create refuses the plugin by name instead of failing a statement later.
- Erasing the data of a plugin drops every object under its prefix, its schema version and every preference document it owns in one transaction on the database thread, and is refused while the plugin runs.
- Exporting writes a consistent copy with `VACUUM INTO` beside its destination and moves it into place only once whole, never over the live database, and importing stages a validated snapshot the same way, which the next start swaps in only after checking again that it is whole, so a staging cut short never replaces the database of the reader, and an import is refused when it carries a plugin schema newer than the number of migrations the installed plugin declares, whether or not that plugin ever ran here.
- Configuration transfers create their snapshot inside an exclusively created private sibling folder, remove only their owned staging and preserve unrelated adjacent files through success or failure. Failure before atomic publication preserves the previous destination.
- A failure to move or remove a database file while a snapshot is swapped in stops the start before any database opens, so an import never loses the database of the reader.
- A database SQLite reports as not a database or as corrupt, or whose schema or version is refused, is moved aside with a timestamp and the reader is told where it went, while a busy lock or a failure to read or write the disk stops the start with its code.
- No code reads or converts a stored layout other than the one the migrations of its owner create.

## C++ implementation standard

- Follow the patterns already in the project, and keep headers, implementations, namespaces, names and ownership aligned.
- Code is compact, professional and consistent, written as an experienced C++ product engineer writes it, without excess vertical space or artificial abstractions.
- Write the new and final version only, without workarounds, fallbacks, legacy paths or compatibility with earlier behavior, and remove or refactor whatever that requires.
- Bundled plugins create their current schema directly before the first stable release, without migrations that create an unused column or index only to drop it, and the schema verification still refuses stored data that differs from the installed declaration.
- A change is made because the product needs it, never to show activity, and nothing unused stays: no dead code, unused API, speculative public member or unbuilt source.
- Every C++ file holds one class or struct named after the file, whose header declares it and whose source defines only its members.
- Every function and every constant is a member of the class it serves, and what only that class uses is a private static member of it.
- A behavior two classes share belongs to the type it describes or to a class named for that responsibility, and a class that only gathers stateless static operations several classes use is a helper named `<Subject>Helper`, such as `Utf8Helper`, so no name ends in `Util`, `Utils` or `Utilities` and no function stands loose.
- A small type used only inside one class is a private nested type of that class, defined in its source when its header does not need its layout.
- An enumeration lives beside the type that owns its meaning, and a vocabulary several types share, such as an axis or an identifier alias, has a header of its own.
- Everything is declared inside the `workpane` namespace, and only the generated application entry point in `cmake/ApplicationMain.cpp.in`, the helper entry points in `src/terminal-main.cpp`, `src/askpass-main.cpp` and the native test launcher in `tests/desktop-main.cpp` stand outside it.
- Related classes share a folder, such as `ui/theme`, `ui/model`, `ui/shell`, `ui/markdown` and one folder per family under `ui/components`.
- The anonymous namespace is never used, so every constant, type and function belongs to a named namespace.
- A member variable carries the `m_` prefix and no identifier begins or ends with an underscore.
- Values, `const`, references, RAII and smart pointers are preferred, and unsafe casts, owning raw pointers and avoidable macros are prohibited.
- Early returns reduce nesting and no `else` follows a branch that returns, continues or breaks.
- Validation, mutation, side effects and returns are separated by blank lines, so a method reads as a beginning, a middle and an end.
- Blocks of different responsibility are separated by one blank line, and independent conditions, validations, loops, mutations and returns are never glued together.
- Nesting is kept shallow, and a condition that ends the work leaves early instead of wrapping the rest.
- A function is extracted only when it is a cohesive responsibility rather than to shorten a method.
- Closed value sets are validated explicitly, and an invalid value produces a structured error rather than a silent default.
- Every result a caller may not drop is declared `[[nodiscard]]`, and a result that is deliberately ignored is assigned to `std::ignore`.
- Nothing in the product ends the process, so no assertion, exception or termination answers a state the code can handle.
- Includes are one group for the header of the file, then project headers, then third party headers and then the standard library, each sorted by the formatter.
- Every file includes the headers of what it names, and a source may rely on what its own header includes.
- Every call, declaration and statement stays complete on one physical line, and the formatter uses an unlimited column width.
- A reader of JSON never holds a temporary, because it keeps a reference to what it reads, and it answers an object, a list or any value as a pointer into what it read, so reading never copies a tree.
- The code uses only what every toolchain of the workflows implements: threads that stop are plain threads with an atomic flag or a condition instead of `std::jthread` and `std::stop_token`, a double is never converted with `std::from_chars`, both of which the libc++ of the macOS runners lacks, and a JSON value is compared with the text of a view as JSON, which the compiler of Microsoft finds ambiguous otherwise.
- A number the product writes or reads for the reader uses a point before its decimals whatever the locale of the process.
- A reader of JSON remembers the fields it read by the values it found, so reading an object never copies the names of its fields.

## Comment standard

- A comment exists only where it is really needed: the intent of a block the names cannot carry, a constraint of a platform or a library, or the reason for a decision the code does not show, and well chosen names make every other comment unnecessary.
- Every comment is a complete sentence that starts with a capital letter and ends with a period.
- A sentence that would start with an identifier written in lowercase is rewritten so the identifier is not at the start, and the identifier keeps its exact spelling.
- A comment above a function, method, class or module, when one is needed, says what it does for whoever calls it, never how it is implemented inside.
- A header carries a comment above a class, struct or enum when one helps, and never a comment describing methods, sections or members.
- A sentence never spans more than one line and never continues on the next one.
- A comment needing more than one sentence ends the current one with a period before the next one begins on the following line.
- Comments are objective and natural, never verbose, fragmented, narrative, decorative or section labels, and never repeat what the code already says.
- A comment sits on what it explains, so it is never followed by a blank line, and no comment divides sentences with a semicolon.
- Code and comments are written in English.
- Repository text and shipped scripts use LF on every platform, so encoded Windows launchers retain their declared command budget after checkout.

## Lambda formatting

- Every C++ lambda is formatted by hand and enclosed by `// clang-format off` and `// clang-format on`.
- Those markers are formatter directives rather than comments and stay lowercase.
- A complex lambda passed to a function is assigned to a named local first, so the call stays complete on one line.

## Lua standard

- A value that crosses into C++ is validated there again, so Lua never relies on the host trusting it.
- An empty Lua table crosses the bridge as an empty object, so the host reads an empty object as an empty list wherever it declares a list.
- A plugin writes every text it shows through its catalog, and every key of its catalog is reached by its code or composed from a family its code names.

## Development workflow and commands

- Development requires Python 3.12 or newer, a C++20 compiler, CMake from 3.29 and Ninja. Platform prerequisites are listed in `docs/getting-started.md`, every task is listed in `docs/development.md` and `python3 make.py doctor` reports tool availability.
- Coverage reads the compiler identity generated by CMake rather than expecting it in the cache, and selects the LLVM reader for Clang, through `xcrun` on macOS.
- The build task `python3 make.py build` builds, the run task `python3 make.py run` runs, and a value after `run` is a data directory for an isolated run.
- The resources are staged again whenever a file under them is added, changed, removed or renamed, so the staged tree always matches the sources.
- The test task `python3 make.py test` builds and runs every test, and the task `python3 make.py all` checks formatting, runs the audits and the tests.
- The format task `python3 make.py format` formats every C++ source, and `python3 make.py format-check` fails on any difference.

- The version is declared once in the project of CMake, which the bundle, the packages, the installer, the build information and the settings read, and the version task `python3 make.py version` prints it or sets a new `MAJOR.MINOR.PATCH`.

## Continuous integration and packaging

- The Build workflow checks formatting and audits once, then builds, tests, packages and validates on Linux, macOS and Windows for x86_64 and arm64.
- Each native workflow saves its digest-keyed dependency cache once compilation succeeds, before application tests, so a failure in first-party behavior never discards a complete dependency build.
- Workflow actions use the supported hosted-runner runtime directly. An action the service reports as requiring a deprecated runtime is upgraded rather than left running through the service's forced runtime replacement.
- Windows workflows select the installed Visual Studio with its native locator and initialize its Developer PowerShell for the runner's host and target architecture. Only environment changes are exported to later steps, without an external JavaScript action for compiler setup.
- Every push to `main` starts the Build workflow without a filter of paths, because GitHub starts no run for a filtered push that changes too many files, and the formatting check installs the release of clang-format the workflow pins, the one the sources are formatted with.
- A tool a workflow installs beyond the runner image, such as Ninja and NSIS on Windows, comes from its release archive pinned by its digest, never from a package feed.
- The Release workflow runs the same builds for a version tag and publishes every package on the release.
- Until the first stable version `main` holds one commit and the repository one release, each change is amended into that commit and pushed with force, the release is published again from its tag, and only the runs of that commit and that release are kept.
- The current version tag is published only after the Build workflow succeeds for the exact commit on `main`. The Release workflow must publish that same commit with every validated desktop package before publication is complete.
- The macOS package is a disk image whose bundle carries the runtime library in `Frameworks` and resources in `Resources` and says in English and Portuguese why pages may ask for the camera and microphone. Packaging signs each native library and helper before its enclosing bundle, using the configured identity or ad hoc. A distribution identity signs every native component with the hardened runtime and secure timestamp and gives camera and audio input entitlements only to the application. Validation checks every nested signature and the application entitlements. The workflows notarize the disk image whenever the secrets hold the identity. Ticket attachment and validation run through the task runner with bounded retries only for unavailable ticket delivery, and every other failure ends the step immediately.
- The Windows package is an NSIS installer laying down `bin` and `share/workpane`, with a desktop shortcut and the runtime of Visual C++ beside the executable, so a machine without its redistributable still starts the product.
- The Linux package is a Debian package under `/opt/workpane` with a desktop entry, an icon and a `workpane` command, whose library dependencies are read from what it links.
- The packages carry only the install component of the product, so no dependency installs anything into them.

## Documentation writing standard

- The README presents the project the way a project page does, with a short introduction, features that name only what the product does in a few words, without its languages, themes, games or installers, which screenshots may show, the download and links to `docs`, while every detail lives in `docs`.
- The development guide `docs/development.md` lists every command of `make.py`, and the audits refuse one that is missing.
- A sentence never begins with code, a path or a fenced block, so a line always opens with a word.
- Every sentence a person reads, in a message, an error, a log entry, a notification, command line output, a comment or a document, is written in sentence case and starts with a capital letter, and a sentence that would open with code, a command or anything else written in lowercase gets a word before it, as in `Use the command "xcrun devicectl list devices" to list them.`
- A commit message is the one text written wholly in lowercase, and a message for a person is one sentence instead of a lowercase label, a colon and a capitalized sentence, so `The task failed because the command "cmake" exited with status 1.` replaces `Task failed: The command...`.
- A command, an option, a path, an identifier or any other reserved expression inside a sentence is marked, with backticks in Markdown and comments and with double quotes in messages, logs and command output, so it never reads as part of the prose.
- Prose never divides sentences with semicolons and never repeats what the code already says.
- This standard writes a number only when the number is the rule itself, such as the version of the language or the oldest version of a system the product supports, and never one that is secondary to a rule, such as the version of a library or of a stored schema, or a limit, a size, a count or a duration the code declares, which it names as the bound the rule keeps.
- The architecture, plugin and component references in `docs` are updated in the same change as the behavior they describe.
- The plan in `PLAN.md` holds the checklist, the review and the review of the review, and every item is checked only when it is built, tested and documented.
- A request too large for one sitting is written first as a detailed list in `MISSING.md`, checked item by item and emptied once every item is done.
- The plan and the list stay on the machine where the work happens, `.gitignore` keeps both out of the repository, and the prose audit covers them while they exist.
